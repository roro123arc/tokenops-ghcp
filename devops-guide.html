Copilot workflows for DevOps teams

Engineering notes based on the questions from our session: how the workflow tools differ at runtime, how to pin and fall back between models, how skills and instructions carry over from Claude Code, how tokens are counted and billed, and how to measure all of it.

1Four kinds of workflow

Is there a difference between Dynamic Workflows, regular workflows and Agentic Workflows?

Four separate tools. They differ in who defines the control flow, where it executes and how it's triggered.

ToolDefined inRuns inControl flow set byTriggered by
Dynamic Workflows.github/extensions/<name>/extension.mjs (JS/TS)Copilot CLI, Copilot app, SDK host, localYour codeA developer: copilot workflow run, SDK, app
GitHub Agentic Workflows (gh-aw).github/workflows/<name>.md → compiled .lock.ymlGitHub Actions runner, agent in a containerYour Markdown instructions + the agentActions events, schedule, manual
Actions workflows.github/workflows/*.ymlGitHub ActionsYAML, deterministicActions events
/fleetNothing persistedCopilot CLI sessionThe model decomposes the goalA prompt

Use

  • Dynamic Workflows for developer-driven, multi-step work that needs checkpoints (migrations)
  • gh-aw for event- or schedule-driven repo automation (CI diagnosis, triage, reports)
  • Plain Actions for build, test, deploy

Avoid

  • Putting a model in a deterministic CI path
  • Using /fleet for a process you need to repeat identically
  • Orchestrating a one-off change that a single prompt can do

2Model pinning, fallback and lost context

Auto lost the context in a long migration. If we pin a model and it becomes unavailable, what happens?

Auto optimizes for availability: some model always answers, but you don't control which. Pinning gives control but a pinned model can be rate-limited, disabled by policy or retired. The failure you saw is a combination of two things: the model changed, and the state of the task existed only in the conversation. Fix both independently.

MechanismWherePins modelPersists task state
Model picker / /modelCLI, IDEPer sessionNo
Custom agent with model:.github/agents/<name>.agent.mdPer agent profile (check per client)No
ctx.agent(..., {model, reasoningEffort})Dynamic WorkflowsPer callYes: journaled steps, pause/resume
engine.modelgh-aw frontmatterPer workflowPer run only
Model policyOrg / enterprise settingsLimits the allowed setNo
PLAN.md, AGENTS.md, Copilot MemoryRepoNoYes, model-independent

Do

  • Pin a primary model for long tasks and name a same-tier fallback in advance
  • Record the resolved model for every step
  • On transient unavailability, pause and resume from the last saved step instead of switching
  • Keep plan, decisions and constraints in files every model reads
  • Keep at least two same-tier models enabled in Model policy

Avoid

  • Silent fallback to Auto inside a multi-step task
  • One long session for a whole migration; use one step per session
  • Assuming any model is always available

3Dynamic Workflows

A repository extension registers one or more workflows with defineWorkflow and joinSession. The CLI supplies the SDK to the extension process. The workflow body is ordinary async code with a context object exposing agents, parallel barriers, journaled steps, phases, logs, pause and cancellation.

copilot --experimental workflow run migrate-module --args @inputs/module-a.json
# observe: /workflows in a session, or the app's Workflows panel

Pinning a model per step

Each agent call carries its own model and reasoning effort. Wrap it in ctx.step so the result is saved and reused on resume.

const plan = await ctx.step("v1:plan", () =>
  ctx.agent("Read PLAN.md and list the steps.",
    { model: "claude-sonnet-5.5", reasoningEffort: "high", label: "plan" }));
await ctx.pause("v1:approve");   // human checkpoint, same run resumes

Explicit fallback instead of Auto

Try the primary model, then a same-tier fallback chosen in advance; if neither answers, pause instead of switching silently. Log which model resolved.

for (const model of ["claude-sonnet-5.5", "claude-sonnet-5"]) {
  const out = await ctx.agent(prompt, { model, label: `fix:${model}` });
  if (out !== null) return out;
}
await ctx.pause("v1:wait-for-model");

Runtime semantics that matter

BehaviourConsequence
ctx.agent returns null on ordinary failure; cancellation, limits and hard failures rejectTreat null as failure. Never let it become an empty success.
Structured output validates a subset of JSON Schema (ranges, patterns, additionalProperties not enforced)Validate semantics in your own code.
Identical prompt + options calls are memoizedUse distinct labels for independent work.
ctx.step key is the only journal identity; recovery is at-least-onceVersion keys (v2:...) when logic changes; make side effects idempotent.
Resume restarts the body and reuses saved steps; unsaved work runs againWrap anything expensive or side-effecting in ctx.step.
ctx.phase is run-globalDon't call it from competing parallel branches.
Concurrency cap queues work; other limits stop the run; maxAiCredits is soft and post-paidA run can overshoot the credit cap slightly.
Paused runs resume; cancelled runs don'tUse pause for review gates.

Security

  • Pre-authorize only required tools: direct copilot workflow run shows no approval prompts
  • Subagents inherit the session's tool grants; scope the session
  • Code-review the extension: it's JavaScript with normal process permissions

Don't assume

  • tools: [] sandboxes the extension (it restricts the agent only)
  • CLI and SDK share session-storage formats across versions
  • Nested workflows (not supported)

4GitHub Agentic Workflows (gh-aw)

A Markdown file with YAML frontmatter (triggers, permissions, engine, limits, safe outputs) and a natural-language body. gh aw compile produces a standard Actions workflow, <name>.lock.yml, that runs the agent in a container.

ControlWhat it does
Read-only tokenThe agent job's GITHUB_TOKEN is read-only by default; secrets are kept out of the agent sandbox.
Agent Workflow FirewallContainer egress limited to approved destinations; optional MicroVM isolation on compatible runners.
Safe outputsThe agent emits proposed writes (issue, comment, PR); a separate, permissioned job validates and applies them.
Threat detectionA dedicated job scans proposed outputs and blocks suspicious changes.
Compile-time checksSchema validation, expression allowlisting, action pinning.
Integrity filteringFilters untrusted GitHub content to reduce prompt injection.
Enginescopilot (default), claude, codex, gemini with the provider key. engine.model per workflow; engine.agent selects a profile from .github/agents/.
Limitsmax-ai-credits (default 1000), max-turns (default 500), Copilot max-continuations.

CI Doctor: diagnose failed runs

Our DevOps skill analyzes CI/CD and environment issues across Jira and GitHub Actions. Can we rebuild it?

Event-driven version. The trigger is a completed CI run on main; the agent reads a trimmed failure excerpt, not the full log, and can only propose an issue.

.github/workflows/ci-doctor.md (key fields)
on: { workflow_run: { workflows: ["CI"], types: [completed], branches: [main] } }
engine: { id: copilot, model: <small model> }
max-ai-credits: <~2x measured>
safe-outputs: { create-issue: {} }   # agent proposes, never writes

Body, in plain language: read the failure excerpt, name the likely cause with quoted lines, check known flaky tests, propose one issue, don't modify code. Then gh aw compile ci-doctor, and inspect runs with gh aw logs / gh aw audit.

Verify against the current gh-aw schema. Field names change between releases; gh aw compile errors are the source of truth.

Cost model for event-driven agents

daily_cost ≈ runs_per_day × (prompt_tokens × in_price + output_tokens × out_price)

Each run is a fresh session, so there is no conversation history, but also little cross-run cache benefit (runs are usually minutes to hours apart). prompt_tokens is dominated by the event payload you inject, typically the log.

IllustrativeNaiveTunedLever
Runs / day3010Failure-only, main + release branches, dedupe same check per PR
Prompt tokens / run22,0004,000Excerpt instead of full log (2,000-token skill unchanged)
Tokens / day660,00040,000
ModelSonnet 5smallengine.model
Input cost / day≈ $1.32< $0.01At $2.00 vs $0.10 per 1M input

Do

  • Run a few times uncapped, read actual usage in gh aw audit, cap at ~2× that
  • Trim inputs in a deterministic step before the agent
  • Keep the agent proposing; route writes through safe outputs
  • Export OpenTelemetry to existing dashboards

Avoid

  • Default caps (1000 credits / 500 turns) in production
  • Triggering on every push or every branch
  • Giving the agent write permissions directly

5Existing Claude-on-Bedrock setups in Actions

If you already run Claude Code in Actions through Amazon Bedrock, that usage is billed to AWS; gh-aw with the Copilot engine bills Copilot AI credits. These are two independent meters, and a migration is a decision about controls and billing, not a requirement.

BillingAWS accountCopilot AI credits (engine copilot) or provider key

6Skills and instructions from Claude Code

Copilot discovers project skills in .github/skills/, .claude/skills/ and .agents/skills/, and personal skills in ~/.copilot/skills/ and ~/.agents/skills/ (Visual Studio also reads ~/.claude/skills/). Supported in Copilot CLI, the Copilot app, the cloud agent, code review and VS Code agent mode. Existing Claude Code skills work without moving.

AGENTS.md                        # Copilot
CLAUDE.md                        # one line: @AGENTS.md
.claude/skills/ci-triage/SKILL.md  # read by both tools

Do

  • Keep each skill in exactly one discovered folder
  • Single source for instructions: AGENTS.md + @AGENTS.md in CLAUDE.md
  • Check allowed-tools: tool names differ (Bash vs shell)
  • Inspect what loads with /context in Copilot CLI

Avoid

  • Symlinking .claude/skills ↔ .agents/skills: Copilot scans both and may load each skill twice
  • Relying on symlinks at all: undocumented for skills, and Git on Windows may not create them (core.symlinks)
  • Pre-approving shell before reviewing the skill's scripts

7Token accounting for skills

If several people use the same skill, how are tokens counted?

Skills load progressively. The cost is per read, not per skill and not per user count.

LayerLoadedBilled
name + description of every discovered skillOn every requestInput tokens, usually cache reads after the first request
Full SKILL.mdWhen the model selects the skillInput tokens on that and following turns
Referenced files, script outputOnly when read or runInput tokens when read
per_day ≈ users × requests × description_tokens + users × uses × skill_tokens
10 × 20 × 50 + 10 × 3 × 2,000 = 10,000 + 60,000 = 70,000 tokens

Counts differ between Claude Code and Copilot for the same skill: different tokenizers, system prompts, tool lists and cache behaviour. Measure in each tool rather than converting.

8Measuring cost of a run

The SDK exposes run-scoped consumption and per-model token metrics. Both are marked experimental in 1.0.19.

const { consumed } = await session.workflow.getRunDetail(runId);   // this run
const metrics = await session.rpc.usage.getMetrics();             // per model
const credits = consumed.nanoAiu / 1e9;                              // nano-AIU → AI credits

Measured live on the public Launch Rescue demo (3 agents, 30 s active), with a cost meter built this way:

ModelRequestsInputCachedOutputAI credits
GPT-6.1 Sol, reasoning max22,35101,2341.82
Sonnet 5.5, reasoning high12,99006861.43
Run total (consumed.nanoAiu)3.25

Per-model credits sum to the run total, so workflow-owned agent usage is included in session metrics. GPT-6.1 Sol produced less visible output than Sonnet but cost more: max reasoning tokens are billed but don't appear in the output column. For gh-aw, the equivalent is gh aw audit; for interactive sessions, /context shows the current window.

9Who pays: SDK authentication and billing

If I build an app on the Copilot SDK, does every user consume my tokens?

Billing follows the credentials the app passes to the SDK.

Auth methodUsage billed toFits
Signed-in user (stored copilot CLI OAuth)That userLocal tools for yourself
COPILOT_GITHUB_TOKEN / GH_TOKEN / GITHUB_TOKENThe token's owner, for every request the app makesAutomation you own; never a shared app
OAuth GitHub App passing each user's tokenEach end user's Copilot allowance (needs a plan)Internal tools for Copilot users
BYOK (Microsoft Foundry, OpenAI, Anthropic keys)Your provider account; no GitHub authPublic or customer-facing apps

Open question. gh-aw's Copilot engine authenticates with copilot-requests: write or a COPILOT_GITHUB_TOKEN secret. The docs don't state which account is billed. BYOK supports key-based auth only (no Entra ID or managed identity). Check terms before building a public app on Copilot credits.

10Model choice and price

Usage-based billing charges every token at the model's API rate. Per 1M tokens, from GitHub's model pricing page:

ModelInputCached inCache writeOutputTypical step
Haiku 5.5 · GPT-6 Luna$0.10$0.01$0.125$0.50Log diagnosis, triage, tests from patterns
Sonnet 5 / 5.5$2.00$0.20$2.50$10.00Planning, multi-file changes
Opus 5.5$4.00$0.20$5.00$20.00Ambiguous design, high-risk changes

Do

  • Cheapest model that passes the step's checks; escalate after two failures
  • Set reasoningEffort per step; reserve max for steps where it changes the outcome
  • Keep a stable prompt prefix (instructions, tool list) so it's served from cache

Watch

  • Haiku 5.5 above 100K tokens per request: price rises ~5×
  • Haiku 5.5 tokenizer counts ~30% more tokens for the same text
  • Long-context tiers (GPT-6 Luna above 272K tokens)

11Subfolders for reusable workflows

Reusable workflows must still live directly in .github/workflows/; the feature request is in the backlog. Composite actions can live in any path, so move shared logic there and keep the reusable workflows thin.

- uses: ./.github/actions/deploy/aws   # composite action in a subfolder
