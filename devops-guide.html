Orientation

Four things called "workflows"

Is there a difference between Dynamic Workflows, regular workflows and Agentic Workflows?

📘 In short

They are four separate tools. The difference is who defines the process and where it runs.

Copilot CLI · app · SDK🧩 Dynamic Workflows

You write the process in code; agents handle the steps that need judgment.

GitHub Actions🤖 Agentic Workflows

Markdown instructions compiled into an Actions workflow.

GitHub Actions · YAML⚙️ Actions workflows

Classic CI/CD with no AI.

Copilot CLI🚀 /fleet

Copilot decides how to split a goal across subagents.

✅ Rules of thumb
  • 👩‍💻A developer drives it and approves each step → Dynamic Workflows.
  • ⏰It should run by itself on an event or schedule → Agentic Workflows.
  • 🧱Build, test, deploy → plain Actions. Keep deterministic steps away from models.
  • 🧭You don't know the steps yet → /fleet. You do → write them down.
  • 💬A quick question or small change → a normal prompt.

Reliability

Auto, pinned models and what happens when a model is unavailable

Auto lost the context in a long migration. But if we pin a model and it's unavailable, what then?

📘 In short

Auto exists so that some model is always available; the price is that you don't control which one runs. The real damage in a long task comes when the model changes and the context lives only in the chat.

So there are two jobs: control which model runs, and keep the context somewhere every model can read it. No guarantee of availability exists; these steps manage the moment a model is missing.

SituationUse
One developer, long taskPinned model + PLAN.md + one session per step
A team repeating the same taskCustom agent with a model field + AGENTS.md
Must be identical every run, with checksDynamic Workflows
Org-wide cost and model controlModel policy
✅ Rules of thumb
  • 📌Pin a model for long tasks. Use Auto for short questions.
  • 🔁Pick the fallback in advance, from the same tier (for example Sonnet 5.5 → Sonnet 5). Switching is fine; switching silently is not.
  • 🧾Log which model actually ran each step, so results can be traced.
  • ⏸️For a temporary outage, wait and resume. In Dynamic Workflows, finished steps are saved and the run continues from the checkpoint.
  • 📄Write decisions to files (PLAN.md, AGENTS.md). Anything left only in the chat will be lost.
  • ✂️One step per session. Start fresh, read the plan, update it at the end.
  • 🏢Keep two same-tier models enabled in Model policy, and watch for model retirement notices.

Local orchestration

Dynamic Workflows

📘 In short

An extension file under .github/extensions/<name>/ defines a process: stages, parallel steps, saved results, a human checkpoint and resume. Each agent call can set its own model and reasoning effort.

ObserveEvidence
→
RouteAdd specialists
→
VerifyChecks in code
→
ApproveHuman
⚠️Verify first. Availability depends on client version, plan, organization policy and model access.
✅ Rules of thumb
  • 📌Set a model on every agent call, and stop the run rather than fall back silently.
  • 🔐Pre-authorize only the tools you need. Direct copilot workflow run shows no approval prompts, and subagents inherit the session's tools.
  • 🔍Review the extension like production code. tools: [] restricts the agent, not the extension's JavaScript.
  • 🔂Make side effects safe to repeat. Resume is at-least-once.
  • ❓Treat a missing answer as a failure. A failed agent call returns null; validate results in code.
  • 💸The credit cap is soft. maxAiCredits is post-paid and can overshoot slightly.

Agents in Actions

Agentic Workflows (gh-aw)

📘 In short

A Markdown file with a YAML header for triggers, permissions and limits, and plain-language instructions below. gh aw compile turns it into a .lock.yml Actions workflow.

  • 🔒 Read-only token by default, no secrets in the agent's sandbox
  • 🧱 Network firewall with approved destinations only
  • ✋ Safe outputs: the agent proposes, a separate job applies
  • 🛡️ Threat detection on proposed output
  • 🔄 Engine: Copilot by default, or Claude Code, Codex, Gemini with an API key
✅ Rules of thumb
  • ✋Let the agent propose, never write. Keep the read-only default and review every change.
  • 🪶Small tasks, small model. Set it per workflow with engine.model.
  • 📏Lower the default caps. Defaults are 1000 AI credits and 500 turns per run. Run a few times, read actual usage in gh aw audit, then cap at about twice that.
  • ✂️Skip what isn't needed. engine.bare: true drops AGENTS.md and other custom instructions.
  • 📊Measure from day one with gh aw logs, gh aw audit or OpenTelemetry export.

Worked example

A CI Doctor that stays cheap

Our DevOps skill analyzes CI/CD and environment issues across Jira and GitHub Actions. Can we rebuild it with workflows?

📘 In short

Yes. Run on demand with approvals → Dynamic Workflows. Run on every failed CI run → Agentic Workflows. For automatic runs, cost is cost per run × number of runs, and the log is usually much bigger than the skill.

Existing setup

Already running agents in Actions on Bedrock?

📘 In short

If you already run Claude in GitHub Actions through Amazon Bedrock, you have a working baseline, billed to your AWS account rather than Copilot AI credits. Moving to Agentic Workflows is a choice about controls (safe outputs, firewall, caps, audit) and about which bill you want.

⚠️Verify first. The gh-aw docs list Claude with an Anthropic API key; we haven't confirmed Bedrock authentication for its Claude engine. Copilot BYOK lists Microsoft Foundry, OpenAI and Anthropic keys.
✅ Rules of thumb
  • 🧮Two meters: Bedrock shows up on AWS, Copilot in AI credits. Compare cost per run on both.
  • 🛡️Compare controls, not only price: read-only tokens, network access, write approvals, spend caps.
  • 1️⃣Move one workflow first and run both side by side for a week.

Migration

Bringing skills across from Claude Code

📘 In short

You don't need to move them. Copilot reads project skills from .github/skills/, .claude/skills/ and .agents/skills/, in the same SKILL.md format, in the CLI, app, cloud agent, code review and VS Code agent mode.

Claude Code reads CLAUDE.md; Copilot reads AGENTS.md.

🚫Avoid symlinking skill folders. Copilot scans several folders, so a symlink can load every skill twice. Symlinks aren't documented for skills and don't always work on Windows checkouts.
✅ Rules of thumb
  • 📍One location per skill: leave them in .claude/skills/.
  • 📝One instructions file: content in AGENTS.md, and one line @AGENTS.md in CLAUDE.md.
  • 🔧Check allowed-tools names (e.g. Bash vs shell). Pre-approve shell only after review.
  • 🧪Test important skills in both tools. Another model can follow them differently.
  • 👀See what loads with /context in the Copilot CLI.

Cost mechanics

How skills use tokens

If several people use the same skill, how are the tokens counted?

📘 In short

A skill costs nothing while it sits in the repo. You pay each time the model reads it, and every use is paid again.

  1. Every request: only the name and description
  2. When used: the full SKILL.md
  3. Only if needed: files it points to
10 developers, 2,000-token skillTokens / day
Description, 20 requests each × 5010,000
Skill used 3 times each × 2,00060,000
Total70,000
✅ Rules of thumb
  • ✏️Keep descriptions short and specific. They travel with every request, for every developer.
  • 📦Move detail out of SKILL.md into files that load only when needed.
  • 🔀Expect different counts per tool: tokenizers, system prompts and caching differ.
  • 📥In automatic workflows the input dominates. Each run starts fresh and the cache has usually expired.

Billing

Who pays for the tokens

If I build an app on the Copilot SDK, does every user consume my tokens?

📘 In short

It depends on which credentials the app passes to the SDK.

AuthenticationWho pays
Your login, or a GH_TOKEN / COPILOT_GITHUB_TOKENYou, for every user
OAuth GitHub App with each user's tokenEach user (needs a Copilot plan)
BYOK: Foundry, OpenAI, Anthropic keysYour provider account
⚠️Verify first. gh-aw's Copilot engine uses copilot-requests: write or a COPILOT_GITHUB_TOKEN secret; the docs don't say which account is billed.
✅ Rules of thumb
  • 🚫Never ship your own token in an app other people use.
  • 🏢Internal tool for Copilot users → OAuth GitHub App.
  • 🌍Public or customer-facing app → BYOK, typically via Microsoft Foundry. Check the terms first.

Actions

Subfolders for reusable workflows

GitHub never added subfolders for reusable workflows.

📘 In short

Reusable workflows still have to live directly in .github/workflows/, and the request is marked as in the backlog.

✅ Rules of thumb
  • 🧱Use composite actions for shared steps. They can live in any path, e.g. .github/actions/build/.
  • 🪶Keep reusable workflows thin; put the logic in composite actions.
  • 📣Raise it through your GitHub account team to add weight.

Next step

Suggested POC: CI Doctor in two weeks

🗓️ Plan
  1. Before: confirm Agentic Workflows are enabled and which account is billed. Note what your current Bedrock setup does.
  2. Week 1: narrow trigger, log-trimming step, small model. Run without tight caps.
  3. Week 2: set caps from week 1's usage, keep it running, review gh aw audit together.
📏 What to measure
  • 🎯Share of failures diagnosed correctly, judged by the engineer who fixed them
  • ⏱️Time from failure to a useful diagnosis
  • 💳AI credits per diagnosis and per week, next to the Bedrock cost of the same task
  • ✅Proposed changes accepted versus rejected
